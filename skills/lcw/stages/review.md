# Review

The finished work is checked against the intent in the spec: first by independent reviewers, then by you, because you hold the intent.

`lcw set health="checking the result against the spec"` (a sweep sets its own words instead, below). On a second or later round, set back only the requirements a fix of the round answers or touches (`lcw req <id> todo`), not their whole groups, and review only those: each gets a new verdict from the reviewer its fix goes back to. The test suites, run in round 1 and again on the head the review settles on, guard the rest.

## The independent review

Round 1 launches fresh reviewer agents, all at once: one for each review group plan.md gives, on the model it gives that group (Opus or Sonnet, effort high). A reviewer with few requirements checks each one properly, and no reviewer holds the whole of a large build. Give each one the path of spec.md, the run worktree, the commit the run branched from (`lcw status` prints it as base; it lets the reviewer see the whole change) and its own requirement ids. Reviewers hand their plain reading and searching to probes.

**A later round goes back to the reviewers that raised its concerns.** Each fix is checked by the reviewer that raised its concern, sent on with SendMessage to its id, which the ledger keeps (Judging, below): it has read the code already, so no fresh reviewer reads it again. Run `lcw usage` first: a message is not a launch, so the launch hook does not stop it at the usage mark. A requirement the fixes touched goes back to its group's reviewer the same way, and a defect two reviewers raised to one of them. Every commit of the round goes to some reviewer: list them, `git log --oneline --first-parent --no-merges <the commit the round's fixes started from>..HEAD` in the run's worktree, and give one the ledger ties to no fix, such as a worker's second commit, to the reviewer of the fix it belongs to.

The message is all the reviewer has to go on, so it says everything:

- each concern it raised, in a line, with the commits that answer it, and any other commit given to it;
- each requirement id it gives a verdict on: those its concerns were about, and those the fixes only touched, named as such, for which it checks that the requirement still holds;
- the commit the round's fixes started from and the head to check at;
- any test a fix's worker did not see fail, by name: it takes that fix out in a throwaway worktree and sees the test fail;
- what to do: read only the commits named to it and say if one changed anything beyond its concern (the same mistake put right in other places is part of the fix, and it checks those places too); run the test files that cover what the fixes touched, by name, and no whole suite; use the thing (pages in a browser at several sizes, say) only in the states the fixes touch; work in a throwaway worktree made new for this, at that head, in a scratch folder not used before, since the one from its first check may be gone or stand at the old commit, and remove it with `git worktree remove` before it reports; reply with pass or failing for each id, then each concern, as before.

Nothing from the ledger goes in the message. Where the ledger holds no id for a concern, or its reviewer cannot be sent on, launch a fresh reviewer in its place, briefed as in round 1 but with the commit the round's fixes started from in place of base: it reads only what the fixes changed.

A walk through every state, where the spec or the charter needs one (no page scrolls sideways at any width, say), runs once, in the first round that leaves nothing else to change. What it finds starts a new round, checked like any later round, and the walk is not run again.

**The suites run in round 1 and on the head the review settles on.** Give one reviewer of round 1, and only one, the job of running the test suites and the repository's own checks before a pull request, as plan.md says, in a throwaway worktree at the round's commit (`git worktree add --detach <a scratch folder> <commit>`), never in the run's worktree. So the round's fixes start as soon as the other verdicts are in, without waiting for the suites, and a fix landing meanwhile cannot change what the suites run. Round 1 is not clean until its suites have reported. A later round runs no whole suite. When one leaves nothing to change, launch one reviewer (Sonnet, high) to run them once more at that head, or launch it alongside a round you expect to be the last; a run counts only for the head it ran on, and what it finds starts a new round. A check tied to a shared service the repository runs from one checkout (a dev stack, say) runs only in a round that leaves nothing else to change, at its head; its failures start a new round, and it runs again in the next such round. The reviewer runs each suite that covers code the run changed, directly or through an import or an API, and may skip one that covers nothing the run touched; when unsure, it runs it. A failing test is a real issue only if the run caused it: the reviewer reruns it at base, in a throwaway copy, and a test that fails there too was already broken. An already-broken test does not hold the run: write it in the ledger (`lcw ledger "already broken: <test>"`).

If the spec lists approved examples, the first round has one more reviewer, with no requirements: its job is the approved examples. Give it the paths of spec.md and plan.md (how each state is reached), the file of each approved state, the run worktree and the run folder. It is the one reviewer a later round does not send on, since its context is full of pictures: launch a fresh one, only if a fix touched something an example shows, and give it only those states. When it reports: `lcw ledger "examples: <n> match, <n> differ, <n> not compared"`.

Record each verdict as it comes:

```
lcw req R3 pass
lcw req R8 failing
```

## Judging

Reviewers never see the ledger, so they challenge decisions made earlier in the run. You hold those decisions and the intent, and every concern gets your call: change the work, or accept it as it is. Weigh a challenge on its merits, not on the fact that a decision was already made: a decision is overturned when the reviewer's point is right. Record each call: `lcw ledger "accepted: <the concern>, because <why>"` for one you keep as it is (the pull request lists those the human would act on), or a fix task for one you change. Something that grows without limit or breaks within months is accepted only for a reason you would defend to the human. An approved example that differs is fixed in the build, never in the example, unless the ledger says why the two cannot match.

If you decided to change anything: `lcw ledger "round <n> fixes start from <git rev-parse HEAD in the run's worktree>; <fix task> goes back to reviewer <its agent id>, ..."` (in a sweep, with `--wave <n>`), naming for each fix task the reviewer that raised its concern, `lcw stage Build`, add a task for each fix (`lcw task add F1 "<fix>" --model sonnet --effort medium`), briefed to put its mistake right wherever it sits, as stages/build.md says under Milestones, have them built as stages/build.md says, and as each fix's worker reports, record what it committed, `lcw ledger "round <n>: <fix task> is <its commit ids>"` (`--wave <n>` in a sweep): the ledger then holds, for each fix, its reviewer and its commits, which is what the round is sent on from after a compaction. Then `lcw stage Review` and run the next round, each fix going back to its reviewer as above.

When no requirement is failing and every fix of a round is to a code comment, a document for people or a test, the next round has one fresh reviewer (Sonnet, high) in place of the reviewers that raised them: it starts small, where each of them would read its whole context again. Text an agent or a program reads, such as a skill, a prompt or a setting, is behaviour, not a document. Give it each concern with the commit that answers it. It checks each fix against its concern and says if a commit changed anything else (the same mistake put right in other places is part of the fix); in a Build it also runs the suites at that head, their run on the settled head, since this round is most likely the last. If a commit did change something else, the round goes to the reviewers that raised the concerns after all.

## Your own check

Judge the whole against the intent in brainstorm.md. Does it do what the human meant? You do not read the diff or run it yourself. Have a reviewer run the thing as the human would use it, in a throwaway worktree at the round's commit, and report what it does for each thing they asked for; then compare that report with the brainstorm. Launch that reviewer with the second round's, or after the first round when it leaves nothing to change. When it reports: `lcw ledger "own check at <commit>: <what you found>"`. This is not a second pass for small things. A real issue you find here goes back to Build like any other, and the next round checks it. Run it again only when fixes made since that commit change what the thing does for the human: with the round that checks them, and only for what they changed.

The review ends when you have made the call on every concern of a round and none needs a change, and your own check finds nothing either. Then:

```
lcw ledger "review passed on round <n>"
lcw stage Ship
lcw checkpoint "Ship: read stages/ship.md and write the draft pull request from brainstorm.md, spec.md and the ledger"
```

and do as it says (SKILL.md, Compaction).

## In a sweep

Each open wave is reviewed on its own, in its own worktree, while the other waves carry on. While several waves are open, or a hunt round runs beside the wave, name the wave in every wave command and in every ledger line and ask about it, such as `lcw ledger --wave <n> "accepted: ..."`: `--wave <n>`. Without it such a line reaches only the run's ledger, and the wave's own, which its pull request is written from, misses it. `lcw set health="reviewing wave <n>'s <count> fixes"`, as SKILL.md says for several waves.

**Take in the wave before first.** A wave cut from an earlier open wave builds on that work, which may have changed since, with review fixes or closures. `lcw wave take` brings in the wave just before it (`lcw/<name>` when none is open), after that wave has taken in its own, so take-ins go oldest first. When it refuses, naming `lcw wave take --wave <m>`, run that one first, but only once wave m has no worker committing (every one of its workers has reported); the command also refuses while one of its tasks runs. Before `lcw stage Review --wave <n>`, which refuses until it is done, and so before every round: `lcw wave take --wave <n>`. If it reports a conflict, it writes a line naming the files to the wave's ledger; launch a worker (Sonnet, medium) in the wave's worktree with the merge command it printed and what each wave's fixes in those files are for, to resolve the merge and commit it, then run `lcw wave take --wave <n>` again. That merge is then this wave's to review, though no round's range shows it, and after a compaction the ledger line says so: give its commit to one reviewer (Sonnet, high), who reads the resolution with `git show --remerge-diff <merge>` and checks it keeps each wave's fixes; where the backlog's closures were in the conflict, it checks each of them again against the evidence, as under Closures below.

A wave is reviewed once, as a whole, as above. Each reviewer gets charter.md, its fixes with their F ids and recipes in place of spec.md and requirement names, the wave's worktree in place of the run's, and the wave's review range from `lcw status`, `git diff <after>...<branch>`, in place of base: it reads only this wave's own changes, never an earlier wave's that it took in. Leave parked fixes out of the groups: they were never built. In a later round, raise the round once back in Review (`lcw wave round --wave <n>`; `lcw wave round <r> --wave <n>` sets it, to put a mistaken raise right); the reviewer each fix goes back to gets the commit the round's fixes started from (the HEAD of the wave's worktree, which the ledger line records), and of the round's own commits, `git log --oneline --first-parent --no-merges <that commit>..<branch>`, reads those its message names, never what a take-in brought; a fresh reviewer launched in one's place reads them all. No round of a wave after the first runs the whole suites, not even one that leaves nothing to change: the wave's final checks are their run on its settled head (stages/ship.md). Each reviewer checks each of its fixes against the recipe: its test shows what the recipe describes and now passes, and for a fix with no test, the item is no longer true. A fix the ledger shows as partly fixed is checked for what it built; when that passes, record it `lcw req <F id> partial`, never pass, so it is not counted as fixed. Name each fix findings.md marks "no proof in the repository" to the reviewers, as a fix with no test by design. Give the reviewer who runs the suites the baseline in charter.md: a test that failed there is already broken and needs no rerun at base. The reviewer who runs the suites also reads the wave's whole change, its review range, against charter.md: nothing in a no-go zone, no kind of change it does not allow, no anti-goal. A check tied to a shared service runs in the wave's final checks (stages/ship.md), not in a round.

**Round 1 runs with the last milestone's check.** A wave you drive yourself enters Review before its last milestone's check has run (stages/build.md): launch that milestone reviewer in the same go as round 1's reviewers, briefed as stages/build.md says, at the commit the milestone ended at, unless the wave's ledger shows that check has already run. Judge its problems with the round's concerns, as one list: two of them may name the same defect, which is one fix. Its fixes are round 1's fixes, X tasks like the rest, and in round 2 each goes back to the reviewer that raised it, the milestone reviewer included; no fresh milestone reviewer checks them. Round 1 is not clean until that check has reported.

**A concern about what the wave did not change.** Reviewers raise everything they see, and some of it was so before the wave's first commit. Such a concern is a new finding, not this wave's fix: write it into findings.md under an id of its own, not yet sorted, as stages/build.md does for what a partly fixed fix leaves, and `lcw ledger --wave <n> "new finding F<id>: <the concern>"`. The next round of Hunt sorts it. Fix it in this wave only when it bears on what the wave ships: the wave's change made it worse or easier to reach, one of the wave's fixes does not work for the person while it stands, or the wave would ship something broken. When you cannot tell, fix it in the wave.

The fix tasks you add to a wave are named X1, X2 and on (`lcw task add X1 "<fix>" ...`), never F ids, which belong to the wave's fixes. When the worker of one reports a test it did not see fail, name that test to the reviewer its fix goes back to, as stages/build.md says.

Your own check judges the wave against charter.md and the wave's findings in place of brainstorm.md.

**Closures, once the review has passed.** No backlog closure is written before this point. When the review passes, `lcw ledger --wave <n> "review passed on round <r>"` and `lcw wave step closures --wave <n>`, then launch one worker (Sonnet, medium) in the wave's worktree to write the wave's closures, once: the rows its passed fixes closed, what is left on a row a fix only partly fixed, the rows its findings showed already fixed, and the items the person's answers closed as decided. Then launch one reviewer (Sonnet, high) with charter.md, findings.md, the fixes with their verdicts from `lcw status` and the closures' commit, to check each closure against that evidence: a row closed only for a fix that passed, partly fixed only for a partial one, already fixed only where findings.md shows it. A wrong closure goes back to a worker, and the reviewer checks again. A wave with nothing to close skips this. If the wave before has moved since the wave took it in, take it in again first (`lcw wave take --wave <n>`): leaving Review is refused until it does. A conflicted take-in here is reviewed as the paragraph on conflicted take-ins above says. Only then does the wave go on to Ship and its final checks:

```
lcw ledger --wave <n> "closures checked"
lcw stage Ship --wave <n>
lcw checkpoint "Ship: read stages/ship.md and ship wave <n>"
```

The checkpoint names every open wave, as SKILL.md says. The wave now holds, so a wave waiting to go back from Ship goes back first (stages/ship.md, "When they fail"); otherwise a queued wave may start, as stages/plan.md says, or the round that follows an early one, as stages/hunt.md says.
